## 4. 编码规范

- 所有 API 返回统一响应结构（如 `Result<T>`：`code` + `data` + `message`）。
- Controller / 路由层保持薄层：只做参数校验、调 Service、包装返回；业务逻辑一律在业务层。
- 数据实体与外部契约（DTO/VO）分离，不直接暴露内部实体。
- 状态、类型等枚举集中管理，禁止在业务代码散落魔法数字/魔法字符串。
- 复杂查询与简单 CRUD 分开：简单走 ORM/默认方法，复杂走手写 SQL 或专用查询对象。

## 5. 架构规则

- 分层依赖单向：路由层 → 业务层 → 数据层，禁止反向或跨层调用。
- 跨多表/多资源的写操作放在单个本地事务内，保证一致性。
- 并发扣减类操作用条件更新（`WHERE 剩余 >= 数量`）防超卖，不用"先查后改"。
- 业务校验失败统一抛业务异常，由全局异常处理器翻译为统一响应，不向上抛裸异常、不吞异常。

## 6. 测试规则

- **单元测试为必须项**：新增或修改业务逻辑必须配套单元测试，不允许"只写实现不写测试"。
- 单元测试覆盖业务逻辑分支，mock 数据层与外部依赖，不依赖数据库与网络。
- 集成测试走完整链路；写数据测试用事务回滚或独立测试库防污染。
- **覆盖率门槛**：核心业务逻辑（事务、状态机、计算）行覆盖率 ≥ 80%，新增代码覆盖率不得低于既有基线。
- 重点覆盖：事务一致性、边界与异常、非法状态迁移。
- 命名：`方法名_场景_预期`，断言到具体值。

## 7. AI 行为规则

> 基于 Karpathy 的 LLM 编码规范（降低 AI 编程常见坑）。这些规则偏向「谨慎优于速度」，简单任务可酌情判断。

### 7.1 先想后做（Think Before Coding）

**不假设、不隐藏困惑、主动暴露取舍。**

- 动手前显式陈述假设；不确定就问，不静默猜测。
- 存在多种理解时，列出选项让用户选，不私自挑一个。
- 有更简单的方案时主动指出，必要时提出异议。
- 遇到模糊点，停下来说清哪里不清楚，提问。

### 7.2 最小改动（Simplicity First）

**只写解决问题所需的最少代码，不投机。**

- 不写需求之外的功能。
- 不为一次性代码引入抽象。
- 不添加未要求的「灵活性 / 可配置性」。
- 不为不可能发生的场景写错误处理。
- 200 行能压到 50 行，就重写。
- 自问：「资深工程师会不会觉得这过度设计？」若是，简化。

### 7.3 外科手术式（Surgical Changes）

**只碰必须碰的，只清理自己造成的烂摊子。**

- 不「顺手改进」相邻代码、注释、格式。
- 不重构没坏的东西。
- 匹配现有风格，即使自己会写得更不同。
- 发现无关的废弃代码，提出来，但不删。
- 只删除自己改动导致的失效 import/变量/函数；不动既有的死代码（除非被要求）。
- 检验标准：每一行改动都能追溯到用户需求。

### 7.4 目标驱动（Goal-Driven Execution）

**定义成功标准，循环直到验证通过。**

- 「加校验」→「先写非法输入测试，再让它通过」。
- 「修 bug」→「先写复现测试，再让它通过」。
- 多步任务先写分步计划，每步带验证点。
- 强成功标准才能独立闭环；弱标准（「让它能跑」）会反复需要澄清。

### 7.5 其他硬规则

- **不编造**：不臆测 API / 库行为；缺上下文先查代码，查不到再问。
- **破坏性操作先确认**：删文件、改表结构、改公开 API 前先告知并获确认。
- **遵循已有模式**：遵循现有命名、分层、错误处理与日志模式，不另起炉灶。
- **bug 修复必登记**：修复 bug 后必须在 `docs/bugfix-log.md` 登记（现象/根因/修复/预防）；若属"本应早知道"的模式问题，同时回写 `docs/skills/` 对应技能的 Common Mistakes。修复前先查 `docs/bugfix-log.md`，同类 bug 不得再次发生。

### 7.6 分阶段开工（先澄清后实现）

新项目从零开始或启动重大功能时，**必须按三阶段推进，一次只执行一个阶段**（详见 `docs/skills/create-project`）：

- **阶段 1 · init**：仅收集「项目名 + 一句话简介」，初始化文档骨架（填充占位符中的名称/简介），不追问技术栈等细节。
- **阶段 2 · requirement_clarify**：与用户讨论需求，产出 `roadmap.md`（顶层开发路线图）与 `docs/requirements.md`（需求文档）。**二者未产出前，不得进入实现、不得拆分任务。**
- **阶段 3 · start_implement**：依据 `roadmap.md` 与 `docs/requirements.md` 拆分任务到 `docs/tasks/`，此阶段才向用户索取语言/框架/构建工具/测试框架/参考项目等具体信息，再搭代码骨架。

逆向禁止：未经阶段 2 的需求澄清，不得直接写实现代码或拆分任务卡。
