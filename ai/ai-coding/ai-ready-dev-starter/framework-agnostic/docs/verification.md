# 质量保障体系

本文定义从实现到交付的验证闭环。目标——**改动必须可验证、可构建、可评审、可对照验收标准**。

## 1. 验证闭环

```
Task（任务卡）→ Implementation（实现）→ Test（测试）→ Review（评审）→ Evaluation（对照验收标准评估）
```

任何改动交付前都应跑完这条链路。任务卡的 Acceptance Criteria 是评估的最终依据。

## 3. 单元测试要求（完善版）

单元测试是本项目质量的第一道防线，**新增或修改业务逻辑必须配套单元测试**。

### 3.1 强制项

- **必须写**：任何新增/修改的业务方法都要有对应单元测试，不允许"只写实现不写测试"。
- **mock 隔离**：单元测试 mock 掉数据层与外部依赖，不连数据库、不连网络，跑得快、可重复。
- **覆盖率门槛**：核心业务逻辑（事务、状态机、计算）行覆盖率 ≥ 80%；新增代码覆盖率不得低于既有基线。
- **命名规范**：`方法名_场景_预期`，如 `createOrder_库存不足_抛异常`，一眼看出测什么。

### 3.2 覆盖场景

每个业务方法至少覆盖：

| 场景 | 说明 |
|------|------|
| 正常路径 | 主流程成功 |
| 边界条件 | 空值、零值、超量、临界值 |
| 异常路径 | 依赖失败、校验失败 |
| 非法状态 | 状态机不允许的迁移 |

### 3.3 断言要求

- 断言到**具体值**（`assertEquals(198, stock)`），不用 `assertNotNull` 凑数。
- 异常断言到**具体异常类型与错误码**。
- 验证 mock 的调用次数与参数（如 `verify(mapper, times(1)).deduct(...)`）。

### 3.4 测试独立性

- 测试之间不共享状态，不依赖执行顺序。
- 每个测试自带数据构造（given/when/then 三段式）。

## 5. 评审（Code Review）

按 `docs/skills/code-review/SKILL.md` 的清单逐项过：

- 分层是否越界
- 是否返回统一响应结构
- 异常是否走业务异常 + 全局处理
- 事务边界是否正确
- 并发安全（扣减是否用条件更新）
- 是否引入 `AGENTS.md` 禁止的中间件
- **是否有配套单元测试、覆盖率是否达标**
- 命名、魔法数字、空指针等基础项

## 6. 评估

以任务卡的 **Acceptance Criteria** 为准绳逐条核对：

- 每条标准是否有对应测试覆盖
- 是否触达 Non Goals 明确排除的范围
- 是否引入新的架构决策（若是，补 ADR）

## 8. 失败处理

- 测试失败：先修测试或实现，不跳过、不掩盖。
- 覆盖率不达标：补测试，不删断言凑数。
- 构建失败：定位编译/依赖问题，不绕过。
- 评审不通过：按意见回开发修订，不改评审标准迁就代码。
